# BurrTools Core API (Target Architecture)

**Status:** Proposal for collaborator review  
**Scope:** The target public boundary of the BurrTools core library — its grid/shape contract, solver session API, calling conventions, and how surrounding layers interact with it. Describes the end state, not migration steps.

---

## 1. Boundary and Design Principles

```
┌────────────────────────────────────────────────────────────────────┐
│  Front ends & hosts: Qt GUI · CLI (burrTxt / burrTxt2) · Python    │
│  Document model · Storage (files / DB) · Solution limits & sorting │
└───────────────────────────────┬────────────────────────────────────┘
                                │
         Grid / Shape contract  │  Solver Session API (pull queue)
                                ▼
┌────────────────────────────────────────────────────────────────────┐
│  Core library (pure computation, no I/O, no GUI)                   │
│  Grids & geometry · Exact-cover engines · Disassembler · Pool      │
└────────────────────────────────────────────────────────────────────┘
```

1. **No I/O in the core.** Solvers and grids never read or write files, databases, XML, `stdout`, or `stderr`.
2. **No shared-document mutation.** Solvers take an immutable problem snapshot and emit owned results through a bounded queue. They never touch a host `puzzle` or `problem` object.
3. **Storage and solver mechanics are private.** Dense arrays, bitsets, coordinate tables, check cells, turn enumeration, and motion planners never cross the public API. Front ends only see grid-neutral shapes, placements, and the resulting motions to display or store.
4. **Crash recovery lives in the host.** The solver never writes checkpoints on its own; a host that wants crash recovery pauses the session, drains the queue, saves the state alongside the results, and resumes.
5. **Same-solver resume only.** Saved search state is opaque and carries no cross-solver, cross-version, or cross-machine compatibility guarantees; incompatible state is rejected with an error.

## 2. Grid, Shape, and Placement Contract

Every grid (cubes, triangular/hexagonal/Cairo prisms, rhombic and octahedral tetrahedra, spheres, cylinders/helices) exposes the same value-oriented interface to front ends, meshers, editors, and storage.

| Concept | Public contract |
| --- | --- |
| **Linear-algebra value types** | Small value types in the public API (`vec3i_t`, `vec3f_t`/`vec3d_t`, `mat3d_t`, `pose3d_t` = physical rotation + translation) for cell lattice translations, physical mesh/geometry coordinates, orientations, and disassembly animation frames — replacing raw `(x, y, z)` out-pointers and `double m[9]` arrays across the core boundary. |
| **Grid** | Immutable value with stable identity (`id`, `name`, `version`) and capability flags (assembly, disassembly, continuous rotation moves). |
| **Cell address `(n, k)`** | Two-part address. `n` (`vec3i_t`) says which copy of the grid's repeating unit cell the cell is in. The unit cell is the parallelepiped spanned by the lattice vectors (the columns of `L`); NG's code calls it the *epiped*. `n` ranges over `ℤ³` for periodic grids and over `(θ mod N, z)` for cylinders. `k ∈ [0, kindCount)` says which of the cells inside that unit cell is meant, so the cell sits at `p = base[k] + L·n` (NG's `getBaseForVoxelPosition`). Embedded `(x, y, z)` voxel coordinates keep rotations linear, but complex grids leave most triples unused (e.g. 24 of 216 in rhombic). With `(n, k)`, every pair with `0 ≤ k < kindCount` is a real cell, translating by `dn` is always valid (`(n + dn, k)`), and oblique lattices suffer no bounding-box bloat. Applying a grid turn goes through the grid (`grid.transform`), which converts privately as needed. |
| **Cell kind** | Each kind has a **space cell** (tiles space without gaps; drives neighbours and editing layers) and a **solid** (drives rendering, STL export, and picking; identical to the space cell except on spheres). |
| **Shape** | Finite set of `(cell, state, colour)` over `(n, k)` where `state ∈ {filled, variable}`. Supports applying a placement, equality up to translation, normalisation, symmetry computation, and basic interactive editor transforms (rotate/mirror). No box sizes, hotspots, or raw embedded voxel arrays in the contract. |
| **Placement & Assembly** | A **placement** `(g, t)` positions a shape (turn + lattice translation `vec3i_t`; e.g. turn index for periodic grids, integer quaternion + mirror flag for spheres) for rendering and serialisation. An `assembly_c` is a list of `(piece, placement)` canonicalised up to result symmetry including mirrors (swapping mirror-partner pieces). |
| **Disassembly (`separation_c`)** | Self-describing disassembly tree/sequence produced by the solver: each move carries the motion needed to animate and persist it (translation step, axial turn, exit push, or continuous pose-space waypoint polyline) and evaluates piece poses as physical `pose3d_t` values without exposing how the solver found them. |
| **Geometry & editing** | Per-kind solid mesh + cell-to-physical-space transform (`pose3d_t`; generic mesher hides shared internal faces, applies `play`/`bevel`, exports STL, supports picking). Layer families expose 2D cell outlines and point hit-testing for grid-neutral editors. |

**Internal to the core (not part of the public API):** enumerating valid piece turns and placements for exact cover (including per-shape rational turns for spheres), deriving or caching check cells for fixed 1-parameter moves (lattice slides, cylindrical axial turns, exits), and running continuous C-space path planning (cube rotation moves in `(θ, du, dv)` against the physical `play`/`bevel` solids). Because all move generation and planning live inside the solver, adding a new grid or motion planner never changes the public grid contract — only the motion kinds a `separation_c` can carry.

## 3. Solver Session API

All solver types live under `src/lib/solver/` and depend only on core math/grid/assembly/disassembly types.

### 3.1 Input: Problem Snapshot & Options

```cpp
struct solverPart_t {
  unsigned int shapeId;   // index into solverSpec_t::shapes
  unsigned int min, max;  // count range, min <= max, max >= 1
  std::vector<std::pair<unsigned short, unsigned short>> groups;
};

struct solverSpec_t {
  std::shared_ptr<const gridType_c> grid;
  std::vector<std::shared_ptr<const shape_c>> shapes;  // immutable copies
  std::vector<solverPart_t> parts;
  unsigned int result;                                 // index into shapes
  unsigned int colours;
  std::set<uint32_t> colourConstraints;
  std::optional<unsigned int> maxHoles;
  std::optional<rotationModel_t> rotationModel;
};

struct solverOptions_t {
  bool reduce            = true;
  bool disassemble       = false;
  bool keepRotations     = false;
  bool completeRotations = false;
  bool rotationMoves     = false;
  bool countOnly         = false;  // count without enqueuing results (the engines still build each assembly internally)
  size_t queueCapacity   = 256;    // soft backpressure bound while Running
  solverSettings_t settings;       // thread count, engine overrides, rotation mode
};
```

- `solverSpec_t` is an immutable snapshot held as `std::shared_ptr<const solverSpec_t>`. Because shapes are copied when building the spec, concurrent edits in a host document can never race a running solver.
- Result storage policies (solution count limits, keep-every-Nth, live sorting, dropping move lists) are **not** solver options; they belong to the host consumer.

### 3.2 Output & Resume Types

```cpp
struct solverResult_t {
  uint64_t seq;                            // discovery index: unique, gap-free, continues across pause/resume and setResume()
  std::unique_ptr<assembly_c> assembly;    // always non-null
  std::unique_ptr<separation_c> separation;// non-null iff disassembled & solvable
};

struct solverRunInfo_t {
  double seconds               = 0.0;
  unsigned long iterations     = 0;
  uint64_t assembliesFound     = 0;
  uint64_t solutionsFound      = 0;
  bool complete                = false;
  std::optional<rotationModel_t> rotationModel;
  unsigned int rotationsSkipped = 0;
  assembler_c::errState error   = assembler_c::ERR_NONE;
  int errorParam                = 0;
};

struct resumeData_t {
  std::string engine;  // solver/engine id, format version, compatibility tag
  std::string state;   // opaque engine search state
  std::vector<std::unique_ptr<assembly_c>> pending; // found, not yet disassembled
  uint64_t nextSeq = 0; // seq the resumed session hands out next
};
```

- `pending` holds engine-independent `assembly_c` objects that exited the assembler before `pause()` but had not yet been disassembled. Keeping them explicit separates the assembler's opaque `state` string from the session's assembly-to-disassembler handoff, and lets hosts reuse their existing assembly serialiser.

### 3.3 Session Control & Queue

```cpp
enum class solverState_e { Idle, Running, Paused, Finished, Stopped, Error };

class solverSession_c {
public:
  // onWake is optional: called with no data when results or a terminal state
  // become available (e.g. QMetaObject::invokeMethod / Fl::awake).
  // May be called from solver threads, possibly while solver-internal locks
  // are held; must not block or call back into the session.
  solverSession_c(std::shared_ptr<const solverSpec_t> spec,
                  solverOptions_t options,
                  std::function<void()> onWake = {});
  ~solverSession_c();  // aborts and joins if still active

  // Optional, legal only in Idle (before start()).
  // Re-instantiates a previously paused search. It is validated by start(),
  // which returns false (session in Error) if the data cannot be used (4.4).
  void setResume(resumeData_t data);

  // Lifecycle controls
  bool start(bool stopAfterPreparation = false);
  void pause();
  bool resume();
  void abort();
  void join();

  // State snapshot: ONLY legal while Paused (error/throw if called while Running).
  // Clones pending assemblies and serialises remaining work so resume() stays valid.
  resumeData_t state() const;

  // Result queue (called on the host's own thread; no external locking needed)
  std::optional<solverResult_t> pop();
  size_t drain(std::vector<solverResult_t> & out, size_t maxItems = SIZE_MAX);

  // Lock-free polled status & progress (safe from any thread)
  solverState_e sessionState() const;
  unsigned int currentAction() const;
  unsigned int currentActionParameter() const;
  float getProgress() const;
  unsigned long getIterations() const;
  uint64_t assembliesFound() const;
  uint64_t solutionsFound() const;
  std::optional<solverRunInfo_t> runInfo() const;
};
```

## 4. Calling Conventions & Semantics

### 4.1 Lifecycle State Machine

| From | Call or event | To |
| --- | --- | --- |
| Idle | `start()` | Running |
| Running | preparation done, with `stopAfterPreparation` | Paused (`onWake` fires) |
| Idle | `start(true)` with resume data | Paused (preparation runs inside `start()`) |
| Idle | `start()` with resume data that cannot be used | Error (`start()` returns `false`) |
| Running | `pause()` | Paused (`state()` is legal only here) |
| Paused | `resume()` | Running |
| Running | search completes | Finished |
| Running | engine error | Error |
| Idle, Running, Paused | `abort()` | Stopped |

- **`start()`:** Builds/reduces the matrix, validates any `resumeData_t`, and launches worker threads (`Idle` → `Running`). If the resume data cannot be used it returns `false` before any worker starts and the session is in `Error`. With `stopAfterPreparation = true`, `start()` returns at once on a fresh run: the session is `Running` while it builds and reduces the matrix and reaches `Paused` when that is done (`onWake` fires), so a host calls `join()` or waits for `Paused` before `state()`. With resume data the preparation runs inside `start()`, so the session may already be `Paused` when `start()` returns.
- **`pause()`:** Stops dispatching new search tasks, drains/parks worker threads and the disassembler pool, and transitions `Running` → `Paused`. Retains the built matrix, reductions, and caches in memory.
- **`state()`:** Legal **only** while `Paused` (precondition failure / exception while `Running`). Returns a complete `resumeData_t` snapshot without consuming the session's live state, so the caller can immediately follow with `resume()` or discard the session.
- **`resume()`:** Legal only while `Paused`. Transitions `Paused` → `Running` in place without rebuilding the matrix or movement caches.
- **`abort()`:** Total and idempotent in any state (`Running`/`Paused` → `Stopped`). Discards in-flight work, wakes any blocked producer or consumer immediately, and produces no resume data.
- **Destructor:** Calls `abort()` and `join()` if active, so destroying a session never leaves dangling threads.

### 4.2 Queue, Ordering, and Backpressure

- **Ownership & thread affinity:** Worker threads (assembler threads, or disassembler pool workers) are the only producers; the host is the single consumer calling `pop()` or `drain()` on its own thread. The host never needs to lock its document against solver threads.
- **Ordering:**
  - Result order is unspecified: results enter the queue as worker threads finish them. With several threads the assembler already hands assemblies on in no particular order, and the disassembler pool delivers them in the order its workers finish. Only the set and the count of assemblies and solutions are promised, the same across thread counts, engines and pause/resume.
  - `seq` is a discovery index, unique and gap-free over the whole search, also across pause/resume and a new session started from `resumeData_t` (`nextSeq`). It need not match queue order.
- **Disassembly filtering:** When `disassemble == true`, every assembly passes through the disassembler before reaching the queue: `separation != nullptr` means a valid disassembly, `separation == nullptr` means an assembly that does not come apart.
- **Backpressure without pause deadlock:**
  - While `Running`, producers block when `queue.size() >= queueCapacity`, keeping memory bounded even on puzzles with millions of solutions.
  - When `pause()` is called, the soft `queueCapacity` cap is lifted for the bounded `O(num_threads)` in-flight results so workers can drain and park even if the host has not drained the queue yet.
- **Blocking vs. batching:**
  - `pop()` blocks until one item is available or the session leaves `Running` (returning `std::nullopt` once empty and non-running).
  - `drain(out, maxItems)` never blocks and moves up to `maxItems` results in one lock acquisition.
- **Count-only fast path:** With `countOnly = true`, the solver updates `assembliesFound()` / `solutionsFound()` internally and enqueues nothing. The engines still build each assembly internally (as the old `solveThread_c` did); only the queue and the host's storage are skipped.

### 4.3 Pause / Save / Resume Invariant

When `pause()` returns:
1. Every result produced before the pause boundary is either already in the queue or in `state().pending`.
2. The host drains the queue (`drain()`), persists those results together with `state()`, and then either calls `resume()` (in-process) or destroys the session (cross-process).
3. On a later cross-process resume, the host constructs a new `solverSession_c`, calls `setResume(saved)`, and calls `start()`.

Under this protocol, pausing at any point loses nothing and duplicates nothing.

### 4.4 Resume Compatibility and Error Policy

- **No guarantees:** A saved `resumeData_t` is only *guaranteed* to resume with the same solver/engine, BurrTools version, build/machine, and problem/options that created it. This limits what is promised; it is not a rule to reject. On another machine or build it may well work, and it will unless the state really cannot be used there (for example, the state of an engine that only exists on x86, continued on ARM).
- **Rejection:** `start()` validates the resume data before any worker thread starts. If it cannot be used (unknown `engine` tag or format version, a problem or options that do not match, malformed `state`, or an engine that cannot run here), the solver makes no attempt to migrate: `start()` returns `false` and the session is in `Error` with `ERR_CAN_NOT_RESTORE_*`.

## 5. How Surrounding Layers Interact with the Core

### 5.1 Document, Collector, and Storage Layer
- Owns the editable puzzle document, file/database I/O, and undo history.
- Builds an immutable `solverSpec_t` snapshot when starting a solve.
- Drains `solverResult_t` batches on the host thread through a host-side collector that applies user-facing policies: solution count caps, keep-every-Nth thinning, dropping move lists, and live sorting ("keep most complex").
- Persists `resumeData_t` (opaque `engine`/`state` strings plus serialised `pending` assemblies) and stores the `rotationModel` reported in `runInfo()` so later runs can detect configuration changes.
- Implements periodic crash recovery on its own schedule: `pause()` → `drain()` → `state()` → persist → `resume()`.

### 5.2 Desktop GUIs (Qt)

The FLTK GUI is not part of the target. Until it retires it uses the session the same way, with `Fl::awake` as its `onWake` hook.

- **Solving:** Constructs `solverSession_c` with an `onWake` callback that posts a queued signal/event to the GUI thread (e.g. `QMetaObject::invokeMethod`). On wake (or a UI tick), calls `drain()` in batches on the GUI thread to update QML/UI models directly — zero cross-thread model locking. Polls `getProgress()`, `currentAction()`, and counters via the lock-free accessors.
- **Pause / autosave:** User Pause calls `pause()` and keeps the session alive for instant `resume()`; autosave calls `pause()` → `drain()` → `state()` → save → `resume()`. Closing or cancelling calls `abort()`.
- **Viewing & editing:** Uses the grid contract's per-kind meshes, generic bevel/STL mesher, picking, and 2D layer outlines/hit-testing — no grid-specific UI code.

### 5.3 Command-Line Tools (`burrTxt`, `burrTxt2`)
- Parse CLI flags and read the input puzzle (file or stdin) outside the core, build `solverSpec_t`, and start a `solverSession_c`.
- Run a plain `while (auto r = session.pop())` loop on the main thread (formatting output directly in `burrTxt`, or feeding the document collector in `burrTxt2`).
- For interactive stop-and-save (`burrTxt2`), call `pause()`, drain any remaining items, store `state()`, and write the output file.

### 5.4 Python Bindings
- Exposes a pull-based iterator over `solverSession_c` with a bounded `queueCapacity`.
- `__next__()` releases the GIL, calls `session.pop()`, and yields the result (or raises `StopIteration` on `std::nullopt`; raises a Python exception if `sessionState() == Error`).
- Closing or garbage-collecting the iterator calls `session.abort()`, immediately stopping background workers without waiting for the rest of the search.

### 5.5 Tests & Headless Batch Drivers
- Construct `solverSpec_t` directly in memory without any document model or XML/file I/O.
- Exercise pause/resume determinism by calling `pause()`, draining, taking `state()`, and verifying that both in-place `resume()` and fresh-session `setResume()` produce identical result sets to an uninterrupted run.
